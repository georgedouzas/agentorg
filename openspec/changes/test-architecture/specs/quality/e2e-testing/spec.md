# Spec Delta

## Purpose

Proves that an org generated by agentorg actually runs. It renders the org, deploys it to a real target, drives real work
through it, checks the outcomes and tears it down. This is the evidence behind the product's core promise.

## ADDED Requirements

### Requirement: The e2e suite is separate from the gated suite
End-to-end tests SHALL live under `tests/e2e/` and run only through `nox -s e2e`. `nox -s tests` SHALL NOT collect them.
They MAY use containers and the network. The unit and integration suite remains network-free.

#### Scenario: Gate unaffected
- **WHEN** a contributor runs `nox -s tests` on a machine without Docker
- **THEN** no e2e test is collected and the session result does not depend on Docker

### Requirement: Deployment targets are a closed set
`nox -s e2e -- --target <t>` SHALL accept one of three targets:
- `local-process`: the rendered node and frontend run as processes, with RabbitMQ and the control plane in containers;
- `local-docker`: the rendered `compose.yaml`;
- `cloud`: the API on Railway and the frontend on Vercel.

An unknown target SHALL fail before any provisioning.

#### Scenario: Local docker target
- **WHEN** `nox -s e2e -- --target local-docker --scenario support-desk` runs
- **THEN** the archetype is rendered with docker packaging, `docker compose up` brings up the node, frontend, control
  plane, database and RabbitMQ, and the scenario runs against the published ports

### Requirement: Every e2e run provisions, exercises and tears down
Each scenario run SHALL go through these phases:
1. render the scenario's spec into a fresh directory;
2. install it;
3. provision the target;
4. wait for health, which covers the node, broker and control plane;
5. exercise the scenario;
6. tear down.

Teardown SHALL run even when an earlier phase fails. Cloud resources SHALL carry the run id in their name.

#### Scenario: Teardown after failure
- **WHEN** a cloud scenario fails during the exercise phase
- **THEN** the Railway and Vercel projects created for that run are deleted, and the run reports the original failure

#### Scenario: Orphan sweeper
- **WHEN** the nightly job starts
- **THEN** cloud projects with the e2e name prefix that are older than 6 hours are deleted first

### Requirement: Model mode is replay, record or live
`--model-mode` SHALL be one of:
- `replay`: the default. The org's `ANTHROPIC_BASE_URL` points at a local mock Messages API that serves recorded responses
  keyed by a normalized request hash.
- `record`: calls the real API and saves the responses.
- `live`: calls the real API without saving.

In `replay` mode, a request with no recording SHALL fail the scenario, naming the request.

#### Scenario: Deterministic replay
- **WHEN** a scenario runs twice in `replay` mode
- **THEN** both runs produce identical run outputs and make no outbound model calls

#### Scenario: Missing recording
- **WHEN** an agent's prompt changed and no recording matches
- **THEN** the scenario fails with a message to re-run in `record` mode

#### Scenario: Live budget cap
- **WHEN** a `live` scenario's accumulated cost exceeds its declared `max_usd`
- **THEN** the scenario is aborted and reported as failed with reason `budget`

### Requirement: Scenarios cover the org archetypes and the master golden path
The suite SHALL include one scenario per archetype: support desk, research and reporting, ops monitoring, content
pipeline, and credit decisions. It SHALL also include a master golden path, which scripts an interview, writes `spec.py`, renders and boots the
result. Each scenario SHALL assert observable outcomes through the public HTTP API and dashboard.

#### Scenario: Support desk outcome
- **WHEN** the support-desk scenario sends a signed webhook
- **THEN** a run reaches `awaiting_approval` on an outbound message, the approval is granted through the API, and the run
  ends `succeeded` with the tool executed

#### Scenario: Golden path
- **WHEN** the golden-path scenario completes its scripted interview
- **THEN** the written `spec.py` validates, renders, boots, and answers a chat message on the target

### Requirement: The dashboard is smoke-tested in a browser
On every target, a browser smoke test SHALL check four things:
- the dashboard loads;
- an agent chat streams a reply;
- the Runs view lists the scenario's runs;
- an approval can be decided from the Inbox.

#### Scenario: Inbox approval in UI
- **WHEN** the support-desk scenario holds an approval
- **THEN** the browser test approves it from the Inbox and the run completes

### Requirement: Failures leave diagnosable artifacts
A failed scenario SHALL save these artifacts under `.e2e-artifacts/<run-id>/`:
- the rendered project;
- node, frontend and broker logs;
- run transcripts from the API;
- the browser trace and screenshots.

#### Scenario: Artifacts on failure
- **WHEN** a scenario fails
- **THEN** its artifact directory exists, and CI uploads it

### Requirement: CI cadence by cost
CI SHALL run the e2e suite at three cadences:
- on every pull request: `replay` × `local-process`;
- on pull requests touching render templates or the operations runtime: also `replay` × `local-docker`;
- nightly and on manual dispatch: `live` × `local-docker` and `replay` × `cloud`.

`live` and `cloud` runs SHALL never run for pull requests from forks.

#### Scenario: Fork PR
- **WHEN** a pull request comes from a fork
- **THEN** only `replay` × `local-process` runs and no secret is exposed
